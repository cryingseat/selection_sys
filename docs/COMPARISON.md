# 两份开源方案的对比与融合

本项目参考了两个导师—学生双向选择系统：

- [BakaRice/tutor-selection](https://github.com/BakaRice/tutor-selection)：Spring Boot + JPA + MySQL 的导师选择系统后端，配套 Vue 前端仓库；
- [fhf-never-code/Mentor-choosing](https://github.com/fhf-never-code/Mentor-choosing)：Spring Boot + JPA + MySQL + Vue 2 的导师学生双向选择系统。

下面先分别分析它们的优点、局限和可复用点，再说明本项目如何融合并扩展为“实训室进组选拔”的完整闭环。

---

## 一、BakaRice/tutor-selection

### 1. 技术形态

- Spring Boot 2.2.5、JDK 11、Maven、MySQL 8、JPA/Hibernate；
- Swagger 2 生成 REST API 文档；
- 自定义登录拦截器、加密解密组件、Header 属性组件；
- 曾尝试使用 Redis 缓存教师课程与教师信息；
- 前端独立仓库 `tutor-selection-vue`。

### 2. 优点

| 优点 | 说明 |
| --- | --- |
| REST 分层清晰 | `Controller → Service → Repository`，接口语义直观，便于前端联调 |
| 有 API 文档意识 | Swagger 让接口可探索，课程项目中很难得 |
| 鉴权有独立抽象 | 登录拦截器 + 角色/uid 加密串，比“前端隐藏按钮”更接近真实系统 |
| 教师评价维度可配置 | 课程权重、最低分限制、内定学生等，体现了“导师侧自主选择”的需求 |
| 前后端分离 | 后端只提供 REST API，前端独立部署 |

### 3. 局限（也是本项目要补齐的部分）

| 局限 | 影响 |
| --- | --- |
| 单轮选择 | 没有批次、阶段、时间窗口，无法组织一次完整的学院选拔 |
| 没有面试 | 导师依据课程成绩/权重直接选择，缺少统一面试记录与考核意见 |
| 没有平行意向 | 学生只能选择一个导师，无法表达多个真实兴趣 |
| 没有多拟录取确认 | 不存在“收到多个拟录取后自主确认”的关键规则 |
| 没有候补、补录、调剂 | 放弃/超额后的名额无法流转 |
| 没有公示与结果锁定 | 最终结果缺少公信力与可追溯性 |
| 权限粒度较粗 | 主要按角色区分，缺少“导师只能看本人/本实训室数据”的细粒度约束 |
| 无审计日志 | 关键操作无法回溯 |
| JPA 实体直接暴露 | 容易把内部字段（如密码摘要）带到接口层；缺少统一 DTO/响应包装 |
| Redis 缓存设计不完整 | README 中作者也提到结构问题导致缓存难加；课程大纲也明确不要求 Redis |

### 4. 可借鉴点

- REST API + 统一响应 + 明确的错误语义；
- 登录拦截器 / 角色校验的独立抽象；
- 导师可配置评价维度（本项目转化为“面试评分 + 评语 + 初选结论 + 候补顺位”）；
- 前后端分离与接口文档意识。

## 二、fhf-never-code/Mentor-choosing

### 1. 技术形态

- Spring Boot 2.2.5、JDK 11、JPA、MySQL 8；
- Vue 2.2 + Vuex 3 + Axios；
- 学生输入学号载入课程；教师导入 Excel 成绩、设置课程权重/最低分、计算综合评分；
- 教师设置实际指导学生数，系统自动校验剩余名额；
- 学生提交前弹出确认，失败时返回友好提示；
- 后台并发判断。

### 2. 优点

| 优点 | 说明 |
| --- | --- |
| 端到端完整 | 前端、后端、数据库、业务规则都能跑通，适合课程项目参考 |
| 名额硬校验 | 教师可设置招生数，系统自动校验剩余名额，避免超额 |
| 并发判断 | 明确考虑多个学生同时提交时的名额竞争 |
| 友好错误提示 | 不匹配、名额满等场景有清晰反馈 |
| 学生确认动作 | 提交前弹确认，减少误操作 |
| 教师参数可配置 | 权重、最低分、招生数均可调整，体现“规则可配置”的思路 |

### 3. 局限

| 局限 | 影响 |
| --- | --- |
| 学生仅输入学号 | 没有密码/身份校验，无法支撑真实选拔场景 |
| 单一导师选择 | 没有 3 个平行意向，也没有“多拟录取选其一” |
| 以成绩加权为主 | 缺少统一面试、评语、候补顺位等过程性评价 |
| 没有批次/阶段/时间 | 无法按学院流程组织宣讲、开放日、填报、面试、确认、补录、调剂、公示 |
| 没有补录/调剂/公示 | 名额流转与结果公信力不足 |
| 没有审计 | 关键操作不可追溯 |
| Vue 2 / JPA | 技术栈偏旧；课程要求 Vue 3 + MyBatis |
| Excel 导入、复杂加权 | 课程大纲明确列为“不做”，不应作为核心依赖 |

### 4. 可借鉴点

- 名额校验 + 并发判断；
- 学生提交前确认、失败友好提示；
- 教师可配置招生名额与规则参数；
- 端到端可运行的产品意识。

## 三、融合策略：保留优点，补齐闭环

### 1. 保留并强化的能力

| 来源 | 能力 | 本项目实现 |
| --- | --- | --- |
| A | REST 分层、统一接口、鉴权拦截 | `Controller/Service/Mapper` 分层；`ApiResponse` 统一响应；`AuthInterceptor` + `@RequireRole` |
| A | 教师可配置评价维度 | 面试评分、评语、初选结论、候补顺位；导师名额可维护 |
| B | 名额硬校验 | 事务 + `SELECT … FOR UPDATE` 锁定导师/实训室，拟录取与最终录取双重校验 |
| B | 并发判断 | 行锁 + 唯一键 + 乐观锁（报名 version） |
| B | 友好错误提示 | 可区分业务码（阶段/时间/资格/名额/面试/锁定等），前端 Toast 精确提示 |
| B | 提交前确认 | 前端关键操作二次确认弹层 |
| A+B | 前后端分离 | Vue 3 SPA + REST API |

### 2. 替换的技术选型

| 原方案 | 本项目 | 原因 |
| --- | --- | --- |
| JPA / Hibernate | MyBatis + XML | 课程要求；复杂名额/状态查询更可控 |
| Spring Boot 2.2 / JDK 11 | Spring Boot 3.2 / JDK 17 | 课程要求；使用 Jakarta API |
| Vue 2 / Vuex | Vue 3 / Pinia | 课程要求；Composition API 更适合复杂页面 |
| Redis 缓存 | 不使用 | 课程边界明确不要求；先用数据库事务保证正确性 |
| Excel 导入、成绩加权 | 不使用 | 大纲明确列为“不做”；避免把选拔简化为唯分数论 |
| 学号直接登录 | 账号 + PBKDF2 密码 + Token | 真实系统需要身份校验与撤权能力 |
| 内定学生 | 不保留 | 与“统一面试、公平选拔、全程留痕”的规则冲突 |

### 3. 大纲要求 → 本项目落点

| 大纲要求 | 落点 |
| --- | --- |
| 集中宣讲 / 开放日 / 时间安排 | `selection_batch` 阶段时间 + `announcement` + 公开首页 8 步流程 |
| 最多 3 个平行意向 | `application_intent`（sort_no + 唯一键） |
| 调剂意愿 | `application.adjustment_preference` + `excluded_lab_ids` |
| 统一面试记录 | `interview`（按报名 + 实训室唯一） |
| 导师初选 / 候补顺位 | `application_intent.status` + `waitlist_rank` + `offer` |
| 导师不能超额 | `SelectionService.lockAndCheckQuota`（导师 + 实训室双重） |
| 学生不能同时加入多个 | `final_assignment(batch_id, student_id)` 唯一 + 确认时释放其他 |
| 多个拟录取选其一 | offer 状态机 + 确认接口 |
| 放弃 / 逾期释放名额 | `OFFER_DECLINE` / `OFFER_EXPIRE` + 管理员处理 + 定时任务 |
| 分轮补录 | `supplement_round` + `supplement_intent` + 候补递补 |
| 统筹调剂 | `adjustment_record` + 内部/跨室/谈话优先级 |
| 公示与锁定 | `publicity` + `StageGuard.assertNotLocked` + 撤回重公示 |
| 操作留痕 | `audit_log`（操作人、角色、时间、对象、原因、IP） |
| 角色与数据权限 | Token 角色 + Service 内数据归属校验 + 导师端屏蔽其他意向 |
| 统一错误信息 | `ErrorCode` + `GlobalExceptionHandler` |
| 前后端接口取数 | 所有页面数据来自 REST API，无写死业务数据 |

### 4. 明确不照搬的部分

- **不做“内定学生”**：与统一面试、公平选拔、公示规则冲突。
- **不做“唯加权成绩”**：保留面试评分与评语，但不把复杂加权排名作为录取依据；大纲明确不要求。
- **不做 Excel 导入导出**：大纲列为不做；管理员可在页面维护学生/导师。
- **不做 Redis 缓存**：先保证事务正确性与可追溯性；数据量级不需要。
- **不做“学生只输学号”**：改为账号密码 + Token，管理员可重置密码、停用账号。
- **不做多学院/多批次并行**：当前实现支持多批次数据，但“当前批次”为单一进行中批次，符合大纲边界。

## 四、融合后的相对优势

1. **流程完整**：从宣讲到公示锁定，10 个阶段、8 个业务步骤全部可操作。
2. **规则可执行**：不是“页面上提示”，而是 Service 层 + 数据库约束共同保证。
3. **并发安全**：名额控制使用行锁，报名修改使用乐观锁，最终录取使用唯一键。
4. **可追溯**：关键操作全部写入审计日志；公示支持撤回—修改—重新公示。
5. **权限清晰**：学生自见、导师本室、管理员全局；导师端主动屏蔽学生其他意向。
6. **技术栈符合大纲**：Vue 3 + Vite + Axios、Java 17 + Spring Boot 3 + MyBatis、MySQL 8。
7. **可演示、可验证**：内置两套批次数据 + 20 项端到端测试，评审可直接复现完整闭环。
